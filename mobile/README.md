# Raunak mobile

Private Flutter attendee app for Android and iOS. Shares Raunak's Firebase accounts and server sessions with the website.

## Included in this first version

- Animated sunburst splash, welcome artwork and bundled Instrument Serif / Geist fonts.
- Light and dark themes, reduced-motion support and small-screen layouts.
- Email/password signup and sign-in, password reset, secure session restoration and sign-out.
- Native Discover with real event cards, debounced search, city autocomplete, date/category/price filters, sorting, pagination and an account sheet. Native Event Details, ticket selection, server-priced checkout, Cashfree payment, verified confirmation and the private ticket wallet.

## Run

From this folder:

```sh
flutter pub get
dart run tool/configure.dart
flutter devices
flutter run --dart-define-from-file=config/local.json -d DEVICE_ID
```

The configuration helper reads only `NEXT_PUBLIC_FIREBASE_API_KEY` from the parent `.env`, or `FIREBASE_API_KEY` from the shell. Its generated `config/local.json` is ignored. Alternatively, copy `config/example.json` to `config/local.json` and enter the Firebase **public web API key** and backend URL. Never use a Firebase service-account key, database URL, payment secret or email credential in this app.

`API_BASE_URL` defaults to `https://raunak.yaduraj.me`. Local HTTP is allowed only for localhost, 127.0.0.1 and the Android emulator bridge 10.0.2.2; development platform network settings may also be required. Use a trusted HTTPS development endpoint for physical-device testing.

VS Code launch configurations are included. Open `mobile/` as the workspace for them.

## iPhone setup

Open `ios/Runner.xcworkspace`, choose your own development team and a unique bundle ID if needed, connect and trust the phone, enable Developer Mode, and keep the phone unlocked for the first installation. Xcode may prepare device symbols during first debugging. A simulator requires an installed iOS runtime. The Android target requires Android SDK tools and accepted licenses.

If device debugging stalls in Apple's loader, verify a profile build independently of LLDB:

```sh
flutter build ios --profile --dart-define-from-file=config/local.json
xcrun devicectl device install app --device DEVICE_ID build/ios/iphoneos/Runner.app
xcrun devicectl device process launch --device DEVICE_ID --terminate-existing me.yaduraj.raunak
```

Xcode runs use the configuration last generated by Flutter. Run a Flutter build with the desired defines before switching to Xcode.

## Authentication

The native client uses Firebase's documented email/password REST endpoints. An ID token is exchanged with `POST /api/mobile/session`; the backend uses its existing Firebase verification, database user sync and HTTP-only session creation. Only the server session cookie is retained in Keychain/Android secure storage. Passwords and Firebase tokens are not persisted. `GET /api/mobile/session` validates restoration and returns only id/name/email. `DELETE` clears the session cookie. Network failure is distinct from expiry, and restoration times out to a retry screen.

The mobile exchange rejects browser-origin requests, bounds request bodies and limits attempts through Redis. Website authentication remains on its existing endpoint. Deploy the matching backend route before using the native app against that environment. No database migration is needed.

The web target is a **visual preview only**. Native session authentication is intentionally unavailable in that preview; it does not circumvent browser cookie/CORS protections.

```sh
flutter run -d chrome
```

## Checks

```sh
flutter analyze
flutter test
flutter build web
```

Authentication tests mock providers and secure storage; widget tests cover navigation, validation, account state and small-screen layouts. A real-device signup/sign-in check is still required before distribution. App Store/Play distribution signing, Google/Apple sign-in and push notifications are later milestones. Paid-payment acceptance on a real device must be completed before launch; automated payment checks use a mocked gateway.

Fonts retain their bundled SIL Open Font License files under `assets/fonts/`.

## Booking and ticket wallet

Checkout uses the existing quote/reservation/reconciliation services. Cashfree order/session identifiers and environment come from the authenticated backend; the app never contains merchant secrets. SDK completion always triggers backend verification. Ambiguous reservation retries retain the same idempotency key, pending orders appear in My tickets, and free bookings skip the payment SDK.

Wallet list/detail routes require the account session and check buyer ownership in database queries. Only active admission details receive the existing signed ticket URL as QR payload; list responses never contain QRs. The wallet revalidates details on resume and while QR views are open, hides unavailable QRs and downloads PDF bytes through the protected existing endpoint. PDF shares contain a private admission ticket: the app explains that it should be kept private.

Subtle system haptics accompany deliberate selections, opening the QR and backend-confirmed booking success. They are not used for polling or loading loops.
